Let the agents build. You review and land.

Il Dolce Far Niente builds several features of your app at once. Each one gets its own Git worktree, its own planner and builder, and fresh reviewers who never saw the build. Nothing reaches your main branch until you say yes.

npx il-dolce-far-niente@latest

Open source, MIT. Works with Claude Code, Codex, GitHub Copilot, OpenCode and Antigravity. Any stack.

Get started in five minutes

Have an app first, in any stack, in a Git repository. Then:

  1. Install

    From the root of your app, run npx il-dolce-far-niente@latest. It adds the skills and a blueprint/ folder for plans and history. Prefer a plugin? See install for your tool.

  2. Onboard

    Restart your agent and run /onboard. It tunes commands and coding standards to your stack and asks for a profile, your issue tracker and models. On an app that already has features, run /adopt instead.

  3. Plan

    Describe the project in blueprint/project-plan.md and list features in blueprint/build-plan.md, or let /discovery interview you. Then /overview.

  4. Set up checks

    Run /ci once. It gives the project one Verify command (typecheck, tests, build) that every landing must pass.

  5. Build

    One feature at a time: /feature, /implement, /check, /complete. Several at once: /plan-graph to mark dependencies, then /avengers.

How a parallel build works

Every feature still gets the full single-feature loop. Only the scheduling changes.

  1. Pick what can start. Build-plan items say what they wait for, like _(after: 2, 3)_. Items that touch the same files, or both touch payments or SMS, go in different waves.
  2. Plan each feature. A planner writes each spec in its own worktree. You approve them all in one packet.
  3. Build in parallel. Builders work test-first, one small verified step at a time, each on its own port.
  4. Review fresh. Reviewers who never saw the build check the standards and the spec, and the security and quality lens when the work is sensitive. Serious findings block landing until a re-review closes them.
  5. Land one at a time. A script archives each feature exactly as a single-feature build would and squashes it onto wave/<n>, rerunning Verify after every landing.
  6. You merge. A final review covers the whole wave. Then it waits for your yes. Nothing is ever pushed for you.

What's inside

AI Blueprint's feature loop

Spec, small verified steps, proof against the running app, fresh review, archive. Plans, specs, findings and history live as readable files in your repo, not in chat.

Matt Pocock's engineering skills

Two-axis code review, test-driven development, triage, wayfinding for foggy projects, architecture surveys and retros, wired into the same files.

A model for every role

By default Opus 5.5 plans and reviews, Sonnet 5.5 builds. Change any role for the team or just for yourself with /models.

Guardrails, not good intentions

Every subagent runs behind a hook that blocks pushes, publishes, deploys and any change to your default branch.

Defaults for real client work

Payments and SMS are always sensitive
PesaPal, Flutterwave, escrow, payouts and Africa's Talking, including their webhooks, always get an audit and independent review, and two of them never share a wave. Add your own categories in the config.
Restricted code stays where it belongs
For classified or regulated work, get the client's written answer on whether code may leave the premises first. A hook enforces it, web research stays off, and a locally hosted model works when the answer is no.
Web and mobile
Verify recipes for Next.js with pnpm, Expo and Flutter, and a mobile check that proves features with widget tests and a simulator screenshot.
Team habits built in
Conventional commits, no AI attribution, consistent branch names, a retro after every wave and a weekly architecture review that files its results.

The commands you'll use most

Set up

  • /onboard Tune a new project
  • /adopt Bring it into an existing app
  • /overview Turn your plans into a project overview
  • /ci One Verify command, locally and on GitHub
  • /models Choose the model for each role

Build one feature

  • /feature Write the spec
  • /implement Build it in small verified steps
  • /check Prove it against the running app
  • /audit Review the code
  • /complete Archive and land it

Build several

  • /plan-graph Mark what depends on what
  • /avengers Build the unblocked features in parallel
  • /avengers resume Pick up an unfinished wave
  • /status See progress and what comes next
  • /mp-retro Improve the setup after a wave

In Codex, type $feature instead of /feature. The full list of 39 commands is in the README.

Questions

Will it push code or touch my main branch on its own?

No. Agents never push, publish or deploy, and a hook blocks them from changing your default branch. A finished wave waits on its own branch until you merge it.

Does it work on an app I've already built?

Yes. Install it, then run /adopt instead of /onboard. It surveys what's already shipped and writes the plans from the code.

Which tools does it need?

Node.js 22 or newer to install, and one of Claude Code, Codex, GitHub Copilot, OpenCode or Antigravity. Parallel builds with /avengers need a tool that runs background subagents with their own model, such as Claude Code. Elsewhere, /continuous builds the plan one feature at a time with the same gates.

Isn't running many agents expensive?

Scripts do the bookkeeping, agents load only the files their role needs, and the merger only runs when a landing conflicts. On a measured four-feature wave this cut the cost by 28% compared with the first version. Set avengers.maxConcurrent to limit how many run at once.

Can I use it on classified or client-restricted code?

Only after the client says in writing whether the code may leave their premises. Choose the restricted profile: it keeps every review gate on, turns web research off, and works with a locally hosted model. See the restricted repositories guide.

Where does the name come from?

"Il dolce far niente" is Italian for the sweetness of doing nothing. The agents do the building; you keep the decisions.
